# Project Review

프로젝트(코드) 또는 문서 데이터를 읽고 현재 상태를 점검한 뒤,
**잘 된 것 → 부족한 것 → 다음 우선순위 3개** 순서로 정리한다.

## 언제 쓰나

- 사용자가 "리뷰", "점검", "현황 정리", "다음 우선순위", "지금 상태 어때" 등을 요청할 때
- 특정 파일/폴더/문서를 지목하면 그 범위만, 지목하지 않으면 프로젝트 루트 전체를 대상으로 한다

## 절차

1. **대상 파악**
   - 사용자가 경로를 지정했으면 그 범위로 한정한다.
   - 없으면 루트에서 시작해 다음을 훑는다: `README*`, `CLAUDE.md`, `AGENTS.md`, `package.json`(scripts·deps), 진입점(`app/`, `src/`, `lib/`, `pages/` 등), 설정 파일(`*.config.*`, `tsconfig.json`, `eslint*`), 문서 폴더(`docs/`), 테스트(`*.test.*`, `*.spec.*`, `__tests__/`).
   - 계획/기획 문서가 있으면(`*.md` in `docs/`, `plan`, `spec`) 함께 읽고, 코드가 그 의도와 일치하는지 대조한다.

2. **증거 수집**
   - 각 관찰은 반드시 **파일 경로**(가능하면 `path:line`)나 **명령 실행 결과**에 근거해야 한다.
   - 필요 시 `lint`, `build`, `test` 스크립트를 실행해 실제 통과 여부를 확인한다(존재할 때). 실행했으면 결과를 그대로 인용한다.
   - 추측·인상 평가 금지. 근거를 못 찾은 항목은 쓰지 않거나 "미확인"으로 명시한다.

3. **판단 정리** — 아래 출력 형식을 그대로 따른다.

## 출력 형식

항상 이 순서·이 제목으로 출력한다.

### (1) 잘 된 것
- 항목별로 한 줄 요약 + 근거(`파일 경로` 또는 실행 결과).
- 예: `lib/score.ts` — 계산 로직이 UI와 분리된 순수 함수, 경계 입력(빈 배열·0) 처리됨. `npm run build` 통과.

### (2) 부족한 것
- 항목별로 문제 + 근거 + 영향.
- 예: 테스트 부재 — `package.json`에 test 스크립트 없음, `*.test.*` 파일 0개. 계산 로직 회귀를 잡을 수 없음.

### (3) 다음 우선순위 3개
정확히 3개. 각 항목에 다음을 붙인다:
1. **무엇을** — 구체적 작업
   - **왜 지금** — (2)의 어느 항목과 연결되는지 / 근거
   - **첫 걸음** — 착수 시 건드릴 파일이나 명령

## 원칙

- 근거 없는 칭찬·지적 금지. 모든 문장은 파일이나 실행 결과로 뒷받침한다.
- 범위를 벗어난 대규모 제안은 우선순위에 넣되, 규모가 크다는 점을 명시한다.
- 사용자가 정한 제약(예: `CLAUDE.md`의 "하지 않는 것")을 위반하는 제안은 하지 않는다. 그 제약 자체가 문제로 보이면 (2)에서 관찰로만 언급한다.
- 코드를 수정하지 않는다. 리뷰와 정리만 한다.
